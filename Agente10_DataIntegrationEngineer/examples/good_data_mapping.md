# Good Example: Data Mapping

> **Why this is correct:** This mapping is complete, bidirectional, has field ownership for every field, PII classification for every field, transformation formulas where needed, and no field is left ambiguous.

---

## Data Mapping: crm-platform ↔ Contact (CORRECT VERSION)

**Mapping ID:** MAP-CRM-001
**Integration ID:** INT-CRM-001
**External system:** crm-platform
**Internal model:** Contact (Prisma)
**Data direction:** Bidirectional

---

### Source → Target (Inbound)

| External Field | Type (External) | Internal Field | Type (Prisma) | Transform | Formula | Nullable | PII | Req. |
|---------------|----------------|----------------|---------------|-----------|---------|----------|-----|------|
| `id` | string | `externalId` | String @unique | DIRECT | — | No | NOT_PII | INT-REQ-001 |
| `email` | string | `email` | String | DIRECT | — | No | PERSONAL | INT-REQ-001 |
| `first_name` | string | *(contributes to)* | — | COMPUTED | see fullName | No | PERSONAL | INT-REQ-001 |
| `last_name` | string | *(contributes to)* | — | COMPUTED | see fullName | No | PERSONAL | INT-REQ-001 |
| *(from above two)* | — | `fullName` | String | COMPUTED | `"${first_name} ${last_name}"` | No | PERSONAL | INT-REQ-001 |
| `phone` | string \| null | `phone` | String? | DIRECT | — | Yes | PERSONAL | INT-REQ-002 |
| `status` | "active"\|"inactive"\|"pending" | `status` | Status (enum) | LOOKUP | See §3 | No | NOT_PII | INT-REQ-001 |
| `company_id` | string | `externalCompanyId` | String? | DIRECT | — | Yes | NOT_PII | INT-REQ-003 |
| `created_at` | ISO8601 string | `createdAt` | DateTime | TYPE_COERCION | `new Date(value)` | No | NOT_PII | — |
| `updated_at` | ISO8601 string | `updatedAt` | DateTime | TYPE_COERCION | `new Date(value)` | No | NOT_PII | — |
| `internal_score` | number | *(dropped)* | — | DROPPED | Internal CRM field — irrelevant | — | NOT_PII | — |

**Why this is correct:**
- Every external field is accounted for (mapped, computed, or explicitly dropped)
- Dropped field has a stated reason
- Computed field formula is explicit: `"${first_name} ${last_name}"`
- Type coercions have the formula documented
- Every field has a `requirement_source`

### Target → Source (Outbound)

| Internal Field | Type (Prisma) | External Field | Type (External) | Transform | Notes |
|----------------|---------------|---------------|----------------|-----------|-------|
| `externalId` | String | *(used as path param)* | — | — | `PUT /v2/contacts/{externalId}` |
| `email` | String | `email` | string | DIRECT | Only sent when INTERNAL_WINS update |
| `fullName` | String | *(split)* | — | COMPUTED | Split at first space: `first_name` + `last_name` |
| `phone` | String? | `phone` | string \| null | DIRECT | null sent as explicit null |
| `syncedAt` | DateTime | *(not sent)* | — | DROPPED | Internal field — not exposed |
| `qualityFlags` | String[] | *(not sent)* | — | DROPPED | Internal field — not exposed |

---

### Enum Map: status

| External Value | Internal Value |
|---------------|---------------|
| `"active"` | `Status.ACTIVE` |
| `"inactive"` | `Status.INACTIVE` |
| `"pending"` | `Status.PENDING` |
| *(any other value)* | QUARANTINE record with error `"Unknown CRM status: {value}"` |

**Why this is correct:** The fallback for unmapped values is explicit (QUARANTINE, not silent default). This surfaces API changes immediately rather than silently assigning wrong status.

### Field Ownership Table ✓

| Internal Field | Owner | Conflict Resolution | Detection |
|----------------|-------|--------------------|---------:|
| `externalId` | EXTERNAL | EXTERNAL_WINS | — (identity field) |
| `email` | EXTERNAL | EXTERNAL_WINS | `updatedAt` comparison |
| `fullName` | EXTERNAL | EXTERNAL_WINS | `updatedAt` comparison |
| `phone` | EXTERNAL | EXTERNAL_WINS | `updatedAt` comparison |
| `status` | EXTERNAL | EXTERNAL_WINS | `updatedAt` comparison |
| `externalCompanyId` | EXTERNAL | EXTERNAL_WINS | `updatedAt` comparison |
| `syncedAt` | INTERNAL | INTERNAL_WINS | — (system-generated) |
| `qualityFlags` | INTERNAL | INTERNAL_WINS | — (system-generated) |
| `createdAt` | EXTERNAL | EXTERNAL_WINS | — (set on first sync only) |
| `updatedAt` | EXTERNAL | EXTERNAL_WINS | — (reflects CRM update time) |

**Why this is correct:** Every field has a declared owner. No ambiguity. Conflict resolution for `email`, `fullName`, `phone` uses `updatedAt` comparison — if the CRM has been updated more recently, the CRM wins. Internal computed fields (`syncedAt`, `qualityFlags`) always win with INTERNAL because they are generated by our system and the CRM cannot produce them.

### Data Lineage ✓

| Internal Field | Source Type | Source |
|----------------|-------------|--------|
| `externalId` | DIRECT | `crm_api.id` |
| `email` | DIRECT | `crm_api.email` |
| `fullName` | COMPUTED | `"${crm_api.first_name} ${crm_api.last_name}"` |
| `phone` | DIRECT | `crm_api.phone` |
| `status` | LOOKUP | `crm_api.status` via enum map |
| `externalCompanyId` | DIRECT | `crm_api.company_id` |
| `syncedAt` | SYSTEM_GENERATED | `new Date()` at upsert time |
| `qualityFlags` | SYSTEM_GENERATED | Set by data quality validation step |
| `createdAt` | TYPE_COERCION | `new Date(crm_api.created_at)` |
| `updatedAt` | TYPE_COERCION | `new Date(crm_api.updated_at)` |

**Why this is correct:** Every internal field has exactly one documented source. No field is "I'm not sure where this comes from." Auditors and implementors know precisely where every bit of data originates.
