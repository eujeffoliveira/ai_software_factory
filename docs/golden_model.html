Golden Model

Padrão técnico de engenharia — Raiz Educação v1.2.0

Este documento define o que fazemos, como fazemos e por que fazemos assim em todos os projetos de software da Raiz Educação. Ele é normativo — seguir o padrão é o caminho padrão, desviar exige justificativa formal.

Princípios

P1

Simplicidade antes de abstração

A solução mais simples que resolve o problema real. Generalize só quando houver repetição real, não antecipação.

P2

Segurança por padrão

A configuração padrão é segura. Qualquer abertura (acesso público, dados em log, auth flexível) precisa ser explícita e justificada.

P3

Auditabilidade

Toda ação humana ou automatizada que afete dados, permissões ou configurações deve ser rastreável via audit_log ou sync_log.

P4

Falhar cedo e claramente

Configurações inválidas e contratos quebrados falham no boot ou CI — nunca silenciosamente em produção.

P5

Zero segredo no código

Nenhuma credencial, token ou chave no código-fonte. Segredos vivem em variáveis de ambiente validadas por lib/env.ts.

P6

Escalabilidade progressiva

Comece simples. Escale quando houver evidência de necessidade. Complexidade prematura cria dívida técnica sem retorno.

Passo a passo

  1. Clone e instale as dependências
    O postinstall roda prisma generate automaticamente.
    git clone <url-do-repositorio>
cd <nome-do-projeto>
npm install
  2. Configure variáveis de ambiente
    Nunca commite .env.local — já está no .gitignore. As variáveis obrigatórias estão documentadas em lib/env.ts.
    cp .env.example .env.local
# edite .env.local com as credenciais fornecidas pelo Tech Lead
  3. Configure o banco de dados
    Use db push apenas localmente. Staging e produção sempre usam migrate deploy.
    npx prisma migrate deploy   # sincroniza com o banco local
# ou, em sandbox descartável:
npx prisma db push          # nunca em staging/produção
  4. Rode o projeto
    npm run dev
# acesse http://localhost:3000
  5. Verifique o baseline
    Se qualquer um desses falhar antes de você mudar algo, sinalize ao Tech Lead.
    npm run typecheck   # TypeScript sem erros
npm run lint        # ESLint sem erros
npm run test        # Vitest — todos passando
npm run build       # build completo sem erros

Regras por camada

✅ Server Components — preferido para leitura

Use para carregamento inicial, listagens, relatórios, páginas protegidas. Acessa lib/db diretamente — sem fetch, sem SWR.

✅ Server Actions — preferido para mutação

Toda mutação passa por aqui. Sequência obrigatória:

actions/dominio.ts 
"use server";
export async function createItem(rawInput: unknown) {
  const session = await auth();
  if (!session) throw new Error("Unauthorized");
  if (!isAdmin(session.user.role)) throw new Error("Forbidden");
  const input = schema.parse(rawInput); // valida com Zod
  await createItemInDb(input);         // chama lib/db
  await logAudit({ action: "create_item", ... });
  revalidatePath("/items");
}

⚠️ SWR — apenas quando necessário

Use somente quando há necessidade real de polling ou filtros client-driven. Sempre com revalidateOnFocus: false.

const fetcher = (url: string) => fetch(url).then(r => {
  if (!r.ok) throw new Error(`HTTP ${r.status}`);
  return r.json();
});
const { data } = useSWR('/api/dados', fetcher, {
  revalidateOnFocus: false,
  refreshInterval: 30000,
});

✅ Use

  • Chamadas a APIs externas

Threat modeling — 5 perguntas obrigatórias

  1. Quem pode chamar este endpoint ou action?
  2. O que acontece se um usuário anônimo chamar?
  3. O que acontece se um usuário autenticado sem permissão chamar?
  4. Quais dados sensíveis passam por aqui?
  5. Existe risco de SQLi, XSS, SSRF, CSRF ou Broken Auth?

O que nunca fazer

  • Logar CPF, e-mail completo ou nome completo em texto claro
  • Armazenar tokens ou cookies em logs
  • Expor stack trace ao cliente
  • Hardcodar qualquer secret no código-fonte
  • Usar process.env.X fora de lib/env.ts
  • Confiar em dados vindos do cliente sem validação Zod
  • Omitir verificação de role em operações administrativas

Jobs & Crons

Idempotência, guardCron e processamento assíncrono

Anatomia de uma cron route

app/api/cron/meu-job/route.ts 
import { NextResponse } from 'next/server';
import { guardCron } from '@/lib/jobs/cron-guard';
import { logSync } from '@/lib/db/sync-log';

export async function GET(req: Request) {
  const guard = guardCron(req);  // ← SEMPRE primeiro
  if (guard) return guard;

  const startedAt = Date.now();
  try {
    const result = await runMeuJob();
    await logSync({ job: 'meu-job', durationMs: Date.now() - startedAt,
      status: 'success', counts: result.counts });
    return NextResponse.json({ ok: true, ...result });
  } catch (err) {
    await logSync({ job: 'meu-job', durationMs: Date.now() - startedAt,
      status: 'error', errorMsg: String(err) });
    return NextResponse.json({ ok: false }, { status: 500 });
  }
}

Paralelismo

✅ Use

  • pMap com limite de concorrência para APIs externas
  • Promise.all para operações independentes

🚫 Não use

  • for...of await em loop paralelizável (sequencial desnecessário)
  • Concorrência ilimitada com APIs instáveis

Exemplos que exigem ADR

📋 Lista completa

  • Backend separado do frontend
  • Worker dedicado ou fila assíncrona
  • Banco diferente de PostgreSQL
  • ORM diferente de Prisma
  • Deploy fora da Vercel
  • Gráficos diferente de Recharts
  • Auth diferente de Google OAuth
  • Serviço Python/FastAPI
  • Pipeline de dados separado
  • Migration destrutiva
  • RLS universal

✅ Não precisa de ADR

  • Novo componente React
  • Nova Server Action
  • Nova tabela no banco
  • Nova coluna em tabela existente
  • Novo job/cron seguindo padrão
  • Refactor interno sem mudança de API
  • Atualização patch de dependência
  • Novo endpoint REST fino
